# Pending — Sri Aparajita → Beyond feature parity (mobile)

**Goal:** bring **all** of Beyond's extra mobile features into the Sri Aparajita mobile app,
**except** SA's product **SKUs / brands / catalogue** (those stay exactly as they are:
Fuchs / Savsol / MFC oils, the six segments `Car·2W·3W·Commercial·Agri·Gear Oil`,
SA's bearings model, **no Filters category**). Done **slowly, one phase at a time.**

Beyond repo: `~/Desktop/Beyond-Distribution-Management-System` · SA repo: this repo.

## Guardrails (every phase)
- Never touch SA's product SKUs / brands / catalogue model.
- **Bearings stay OUT of the mobile order screen** (oils-only, brand tabs) — confirmed 2026-10-14.
- Adapt Beyond code to SA's own types (oils-only, Fuchs/Savsol/MFC brand tabs, six segments, SA bearings).
- API/DB/web changes ARE allowed where a feature requires them (e.g. follow-ups) — confirmed 2026-10-14.
- Per phase: `tsc` + tests + on-emulator verify + ship (OTA for JS-only, APK for native).
- SA git rules: never `git add -A/.`, never push/deploy without asking, never `--no-verify`.

## Known baseline (verified 2026-10-14)
- SA API **already has `clientUuid` idempotency** on orders/collections/visits/deliveries → offline writes are mostly a **mobile-side** job.
- SA has **no follow-ups** (API or mobile); SA migrations are on their own track (latest `0094`), Beyond's `0090_customer_followups` is NOT in SA → follow-ups = **API + DB + mobile**.
- SA local SQLite is at schema **v20** but **lacks the offline order/sync tables**; its schema diverged from Beyond's → offline tables added as **new** migration steps, not copied.
- SA order flow = oils-only, **brand tabs** (Fuchs/Savsol/MFC), **online-only**; shares Beyond's order UI component filenames but each has drifted.

## Phase 2 — Offline writes, one feature at a time  *(each independently shippable)*
- [x] **2a check-in / visits offline** (2026-10-14): the queue is now **live**. `kickSync` flushes the write-queue via a per-entity transport (`sync-send`); `visit-queue.ts` (`recordVisitCheckin`/`ensureCheckoutQueued`) writes the local `visits` row + enqueues. `performCheckIn` is online-first (offline → queue, returns the clientUuid handle); `performCheckOut` resolves the server id from the local visit row (online server-driven no-outcome flow kept; offline → prompt reason proactively + queue; a dropped-mid-request network error falls through to the queue). `applyServerResult` maps the server visit id back onto the local row (FIFO guarantees check-in syncs before its check-out).
