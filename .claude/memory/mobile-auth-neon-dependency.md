**Reported 2026-10-10:** SEs on weak 4G (a) can't log in — screen shows `fetch failed: java.net.UnknownHostException: Unable to resolve host "ep-proud-forest-b3snqhvr.neonauth.c-4.ap-southeast-1.aws.neon.tech": No address associated with hostname` — and (b) get **auto-logged-out** mid-use. "Works after switching the phone off and on" = a stuck negative-DNS/resolver state cleared by a network-stack reset.

**Root cause (both symptoms):** the mobile app talks to the **Neon Auth host DIRECTLY from the device** for login (`neonSignIn` → `/sign-in/email`) and for minting the short-lived (~15 min) API JWT (`neonJwtFromSession`/`neonProbeSession` → `/token`), in `apps/mobile/src/lib/neon-auth.ts`. That deep `…aws.neon.tech` host is unreliable to DNS-resolve on mobile carriers, while the API host (Cloudflare `…workers.dev`) resolves fine — an asymmetry that:
1. **Login:** a DNS failure throws `UnknownHostException` → login dead (no retry/timeout; raw error shown).
2. **Auto-logout:** API JWT ages out → the (reachable) Cloudflare API returns 401 → the app refreshes against the (unreachable) Neon host → the refresh primitive returned `null` on *any* failure (network == revoked) → `api.ts` called `notifyAuthExpired()` → token dropped → login screen. The `use-session-guard.ts` was already offline-safe (only logs out on a definitive 401/403 "revoked"), but the token-refresh/401 path was NOT — that inconsistency was the bug. Confirmed by reproducing the exact `UnknownHostException` on the emulator by pointing the Neon host at a `.invalid` TLD.

**Phase 1 — SHIPPED 2026-10-10 via OTA** (JS-only; channel `production`, runtime `9796be6d…`, update group `97ec26dd-599c-4275-a236-c5107df004c4`). Files: `token-refresh.ts` (new `RefreshOutcome = active|revoked|unavailable`; a thrown/failed mint = `unavailable`, never a logout), `auth.ts` (minter now uses `neonProbeSession` to classify, not blind `neonJwtFromSession`), `api.ts` (401 handler only `notifyAuthExpired()` on `revoked`/truly-dead; on `unavailable` it throws an `OFFLINE` error and KEEPS the session), `neon-auth.ts` (`neonFetch` adds a 12s timeout to all Neon calls; `neonSignIn` retries the network attempt 3× with backoff — but NOT on a 4xx), `humanize-error.ts` (regex now catches `UnknownHostException`/"resolve host"/"no address"), `use-login-form.ts` (shows the friendly "Check your signal and try again." for network errors, but the real server message for a 4xx like wrong password). New test in `api.test.ts`: a 401 whose refresh is `unavailable` must NOT log out.

**Phase 2 — SHIPPED 2026-10-10** (commit `b18960e`; API deployed version `086a9fc0`; mobile OTA update group `369b0ea1-7817-4706-b1f3-ba48ace0123f`, runtime `9796be6d…`). Auth now routes through the Cloudflare API so the **device never resolves the `neon.tech` host** — the real cure for the stuck-negative-DNS case. **It was OTA-able after all** (mobile change is JS-only: `neon-auth.ts` calls `/auth/*` on `API_BASE_URL`; fingerprint unchanged), NOT a new native build — only the API needed deploying. New API: `apps/api/src/routes/auth.ts` (public, mounted before the billing gate) + `apps/api/src/services/mobile-auth.ts` (server-side Neon REST: sign-in/mint/sign-out, 12s timeout, Origin via `NEON_AUTH_ORIGIN` env default `http://localhost:3000`, a trusted origin). Endpoints: `POST /auth/login`→{session,token,user}, `POST /auth/token`→3-way {status: active|revoked|unavailable}, `POST /auth/sign-out`. `NEON_AUTH_BASE_URL` was already a deployed Worker secret. **Rollout order that MUST hold: deploy API before the OTA** (else apps call `/auth/*` before it exists); apps that haven't pulled the OTA keep the old direct-to-Neon path, which still works, so no mid-rollout breakage. Verified: deployed `/auth/login`→401 on bad creds, `/auth/token`→revoked on a bogus session; on emulator with the API down, login fails with a connection error (proves it no longer calls Neon directly).

**Live-verified 2026-10-10** on the production build (both OTAs applied) with a real logged-in SUPER_ADMIN session: put the emulator in airplane mode (dead zone) and backgrounded/foregrounded the app 3× (each resume fires the session-guard refresh) — it STAYED on the Dashboard, showed the offline bar, and never bounced to login (no `expireSession`/`auth-expired`); reconnecting recovered cleanly. This is the reported auto-logout symptom demonstrated fixed on a real session.

Caveat: this moves the device's dependency from `neon.tech` → `*.workers.dev` (far more reliable). If a carrier ever blocks workers.dev too, move the API to a custom domain.

Caveat: do NOT bump `app.json` version for an OTA — it breaks runtime matching (see [[expo-ota-updates]]). Verify/test OTA on emulator per [[android-emulator-and-ota-testing]].
