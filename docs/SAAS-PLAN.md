# Distribution OS — SaaS Plan

**Distribution OS** is a SaaS product that **many enterprises** use (web + Android + MCP + billing). Every enterprise has its own sales executives, delivery persons, accountants, and managers, and all data is **separated by enterprise** (`enterprise_id`).

> **Status: PLANNING ONLY — do not write code yet.** This document is the deliverable for now; implementation comes later.

> **Build approach:** Distribution OS is a **clone of this entire codebase into a new project/repo**, rebranded from "Sri Aparajita" to **"Distribution OS"**. The owner will provide the fresh API keys (Razorpay, Neon, Cloudflare, Neon Auth, EAS/Play, PostHog, maps). The **existing Sri Aparajita system stays on its own deployment, untouched** — this work does not modify it. Whether/when Sri Aparajita is later onboarded into Distribution OS as an enterprise is an open decision (below).

> Terminology: a customer company that buys our product is an **enterprise**. We never say "tenant." The isolation key on every table is **`enterprise_id`**.

## Target architecture

### 1. Enterprise separation

> ✅ **ISOLATION MODEL — LOCKED 2026-11-11: ONE shared DB + `enterprise_id` + Postgres RLS.** The owner chose a single shared database for all enterprises (over the earlier DB-per-enterprise lean). Guardrails (all three, given this is financial data): a **mandatory enterprise-scoped SQL helper** that injects `enterprise_id = $current` on every query, **Postgres Row-Level Security** keyed on a per-request `app.enterprise_id` GUC, and automated **cross-enterprise leak tests** (Phase 8). Trade-off accepted: *logical* isolation only (a single missed filter / RLS gap could leak a competitor's financial data — the reason for the two defence layers below), and backups/restore/delete operate at the whole-DB level, not per enterprise (the DB-per-enterprise option, which gave per-enterprise backup/restore/delete + physical isolation, was considered and declined). The admin cockpit (control-plane) is unaffected. The rest of §1 is the shared-DB design.

- New global **`enterprises`** table: `id`, `name` (legal), `slug`, `status` (`pending|trial|active|grace|blocked|suspended`), `created_at`. Core company identity lives here. (`pending` = signed up, awaiting owner approval.)
- Add `enterprise_id uuid not null references enterprises(id)` to **every enterprise-owned table** (users, customers, products, `product_packs`, product_segments, orders, order_items, invoices, collections, visits, beat_plans, gps_points, tracking_*, tasks + comments/attachments, market_notes, attendance, expenditures, se_targets, push_tokens, se_notifications, customer_dues_state, **the stock ledger** (`stock_locations`, `stock_movements`, `stock_balances`, `stock_lots`, `stock_reorder_state`, `goods_receipts`/`goods_receipt_items`, `stock_transfers`/`stock_transfer_items`, `stock_adjustments`/`stock_adjustment_items`, `opening_stock_items`), **invoicing** (`invoices`, `invoice_items`, `invoice_line_allocations`, `invoice_series`, `sales_returns`, `sales_return_items`), `margin_simulations`, `customer_opening_balances`, billing_charges, payment_proofs, `system_settings` → PK `(enterprise_id, key)`, …). **Global tables stay global**: `roles` (SUPER_ADMIN / MANAGER / ACCOUNTANT / SALES_EXECUTIVE / LOGISTICS are the same everywhere), `enterprises`, `schema_migrations`, platform-admin tables.
- ⚠️ **Invoice numbering is per-enterprise** — `invoice_series` must scope the GST invoice sequence to each enterprise (every enterprise runs its own number series; no shared counter). Likewise **FEFO lot costing, `cogs_amount`, and the Profitability report must all be enterprise-scoped** — a sale may only draw `stock_lots` belonging to the same enterprise, and cost/profit never crosses enterprises.
- **Isolation = two layers (both, given this is financial data):**
  1. **App layer** — auth context carries `enterprise_id` (from the user's row / JWT claim); a mandatory enterprise-scoped SQL helper injects `enterprise_id = $current` on every query. Add a lint/review gate so no raw cross-enterprise query slips in.
  2. **DB layer (defense-in-depth)** — Postgres **Row-Level Security** policies keyed on a per-request `set app.enterprise_id` GUC (Neon supports RLS). This is the hard guarantee against a missed filter.
- **Auth** — each user belongs to exactly one enterprise; login resolves the enterprise from the account; JWT gains an `enterprise_id` claim; the Neon-Auth app-profile mapping gains `enterprise_id`. (Roles like SALES_EXECUTIVE/LOGISTICS/ACCOUNTANT/MANAGER are assigned within an enterprise.)
- **Login identity (new capability)** — a user signs in with **email OR phone number + password**; both are **globally unique** across all enterprises (so either one resolves exactly one account → one enterprise). Today only email login exists; phone+password login must be added (web + mobile). Decide hashing/reset flow for phone accounts alongside the existing Neon-Auth email path.

### 2. Owner dashboard — a separate control plane (for the owner — "make my life easy")
- A **dedicated owner dashboard**, a surface of its own (not a page inside the enterprise app, and gated to the platform owner — a super-super-admin distinct from any enterprise's SUPER_ADMIN). On its own **`admin.`** subdomain with its own auth — **single owner account, email + password via Neon Auth with an owner flag**.
- Day-one jobs: **approve/reject** pending enterprise signups (queue), set/override each enterprise's **custom price**, view **payments & billing status** across all enterprises, suspend/activate/close an enterprise, and **impersonate** an enterprise for support (**every impersonation audit-logged**: who, which enterprise, when, read vs write).
- **Built to grow** — the owner expects to add more here over time (analytics across enterprises, usage, dunning, support tooling), so design it as an extensible cockpit, not a one-off page.
- **📄 v1 detailed spec → [`docs/ADMIN-DASHBOARD-PLAN.md`](./ADMIN-DASHBOARD-PLAN.md).** **v1 scope updated 2026-11-11** — the cockpit is built **together with onboarding** and now includes the **signup approval queue** (review a pending company's full profile → **Approve + set price** in one step, or **Reject with a reason** → applicant edits + resubmits), the **enterprises list + status**, **per-enterprise billing** (set price · charge+payment ledger · manual paid/comp override), and the **GST subscription-invoice upload** (your own series, enterprise downloads it, replace-to-correct). **Suspend/activate, impersonation, and cross-enterprise analytics stay deferred.** Billing basics (locked 2026-11-06): charges **auto-generated on the 1st**, **per-seat or flat, base + 18% GST**, **Razorpay-only, paid in the enterprise app** (no manual/partial entry). The cockpit touches only **control-plane tables**.

### 3. Pricing & billing (fully custom per enterprise, manual monthly)
- New **`enterprise_billing_config`**: `enterprise_id` (pk), `model` (`per_seat|flat`), `unit_amount_paisa` (per_seat), `flat_amount_paisa` (flat), `gst_rate` (**flat 18%** for everyone in v1), `currency` (`INR`), `status`. (No `billing_day` — see next line.)
- `billing_charges` gains `enterprise_id`. Charges are **auto-generated on the 1st of every month** for all active enterprises (one common date). The generator computes per enterprise from config (per_seat = unit × that enterprise's **active users, snapshotted on the 1st**; flat = fixed), **base + 18% GST**. The existing `free/active/grace/blocked` state machine + banner (`billing-guard-v2`) + blocked screen become **per-enterprise**.
- **Payment = Razorpay only, paid inside the enterprise's app** (existing flow, now scoped); the webhook marks the enterprise paid/active. **No manual payment recording, no partial payments.** The owner has a **manual override** to mark paid/active without Razorpay (comp/free/settled). Platform-admin sets each enterprise's custom price.
- **GST subscription invoice = owner uploads a PDF** (generated elsewhere) + types metadata, against each month's charge, under the owner's **own invoice-number series**; the enterprise downloads it in their app; **replace-the-file to correct** (no credit notes). Detailed in [`docs/ADMIN-DASHBOARD-PLAN.md`](./ADMIN-DASHBOARD-PLAN.md).

### 4. Self-serve signup + onboarding

> **📄 Full detail → [`docs/ONBOARDING-PLAN.md`](./ONBOARDING-PLAN.md)** — the signup page, the multi-step onboarding wizard (every field mandatory, draft auto-save), what Submit writes, and the owner's approval + pricing. Locked with the owner 2026-11-11.

- **Signup = login only** (public, outside dashboard auth): **email + phone + password**, both **globally unique** across all enterprises. **Email OTP-verified** (v1; phone stored + uniqueness-checked, phone OTP later). Creates the account only — **no enterprise yet**.
- **Onboarding wizard** (after signup): a **multi-step** wizard, **every field mandatory (no skip)**, with **auto-saved draft** (resume where left off on next login). Collects the whole Settings-page profile for the new company: admin name · company legal name + **GSTIN** + contact · registered address · bank + UPI · invoice series (prefix/start) · **invoice Terms & Conditions** (pre-filled with the standard default, editable) · ≥1 godown · field-tracking auto-stop times (**separate SE + Logistics**) · **custom dues-ageing bands** (variable count; each band has a from–to day range + custom label; bands cover **overdue money only**, aged by **days since invoice date**). Dues-sweep stays a fixed ~9 AM daily job (not a field). **No company-wide credit-overdue field** — see the overdue-model change below.
- **On Submit**: the enterprise is created **`status='pending'`** with all its config written (scoped by `enterprise_id`). **Nothing is usable until approved.**
- **Owner approval** (in the owner dashboard, §2): the pending company appears in the **approval queue**; the owner reviews the full profile and either **Approves + sets the price** in one step (per-seat or flat + amount → `status='active'`, billing starts, enterprise defaults seed, SUPER_ADMIN activates) or **Rejects with a reason** → the applicant is notified and can **edit their onboarding and resubmit**.
- ⚠️ **Overdue-model change (ripples beyond onboarding):** the single company-wide `credit_overdue_days` grace is **removed**. A customer is overdue + **credit-blocked as soon as they are past their own `credit_days`** (i.e. past the invoice `due_date = invoice_date + customer.credit_days`), with no extra grace. This changes the mobile **credit gate** (`getCustomerCreditStatus` in `services/customers.ts`) and the **dues ageing**: the dues bands (web dues card + mobile oldest-bucket dues, both hardcoded `0-30/31-45/46-60/61+` today) become the enterprise's **configured bands**, applied to overdue invoices only, aged from the invoice date.

### 5. Mobile (one shared app, Play Store)
- Rebrand `apps/mobile` to a neutral product name + new package id + new EAS project. API URL stays single (shared API); the user's enterprise is resolved server-side from their token — **no per-enterprise client logic**. A sales exec / delivery person / accountant / manager just logs in and lands in their enterprise.
- **Play Store** setup: Play Console, privacy policy, **data-safety + background-location declaration** (the field-tracking foreground service needs a solid justification for review). One OTA bundle reaches all enterprises.
- Use the fresh Play APK as the moment to **fix the `runtimeVersion` policy** so future OTAs stop needing the pin hack (see memory `expo-ota-updates`).

### 6. MCP (per-enterprise, scoped)
- Make `apps/mcp` enterprise-aware: the passphrase/token maps to an `enterprise_id`; `runReadOnlySql` injects `enterprise_id = $ent` (or sets the RLS GUC) so every read is confined to that enterprise. One shared MCP Worker; enterprise resolved from the credential. Each enterprise manages enable/passphrase in their own Settings → MCP page.

- **Phase 5 — Mobile rebrand + Play Store + runtime-policy fix + OTA.** Full detail → [`docs/MOBILE-SAAS-PLAN.md`](MOBILE-SAAS-PLAN.md): enterprise-aware login (`/me` + JWT carry `enterprise_id`), **neutral branding everywhere** (no per-enterprise logo), **fully server-driven dues bands** (drop the fixed 4-bucket union, OTA-able), tracking auto-stop from the enterprise's onboarding config (native, in the APK). - **Phase 6 — Hardening.** Automated **cross-enterprise leak tests** (web + API + MCP paths), per-enterprise observability, rate limits, backups. Then (deferred features) suspend/activate, impersonation, cross-enterprise analytics, phone OTP.
