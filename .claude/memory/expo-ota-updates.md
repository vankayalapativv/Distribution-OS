Mobile app (`apps/mobile`, Expo SDK 57) ships JS-only changes over-the-air without a rebuild. Set up 2026-10-04.

**Ship command** (JS-only changes only):
`cd apps/mobile && npx eas-cli update --channel production --platform android --environment production --message "<what>"`

**Gotchas (all load-bearing):**
- **ALWAYS `--platform android`.** App is Android-only; default "all" tries to bundle web and fails (expo-sqlite wasm).
- **`eas update` bakes `EXPO_PUBLIC_*` from the EAS *environment*, NOT from `eas.json` build-profile `env`.** All three runtime vars are now registered as EAS env vars in production/preview/development: `EXPO_PUBLIC_API_URL`, `EXPO_PUBLIC_NEON_AUTH_BASE_URL`, `EXPO_PUBLIC_NEON_AUTH_ORIGIN`. If any were missing, the OTA bundle would ship it undefined and the app falls back to localhost → every API call fails ("Something went wrong") while the APK stays fine. Manage with `eas env:create/list`.
- **Runtime version = fingerprint** (`app.json` runtimeVersion.policy "fingerprint"). An OTA reaches an installed APK only when the APK's Runtime Version AND Channel match the update. JS-only changes keep the fingerprint; a NEW native dep/plugin/config change shifts it → cut a new APK before OTAs land again. Verify with `eas build:list --platform android` (compare Runtime Version + Channel) vs the `eas update` output's Runtime version.
- **Channel mapping**: the `indus` build profile extends `production`, so indus store APKs run on `channel: production`. The field devices' installed build is the indus/production one (runtime `9796be6d…` as of 2026-10-04).
- **BUMPING `app.json` `version` BREAKS OTA DELIVERY** (confirmed 2026-10-09, @expo/fingerprint@0.20.3): `expo.version` IS in the fingerprint — 1.1.2→1.1.3 shifted the android hash `9796be6d…`→`bf4dc3c6…`, so an OTA at the bumped version skips all installed 1.1.2 devices. **Can't both bump the version AND OTA to current devices** — keep `version` unchanged for an OTA, or cut a new APK to change it. Settings shows `Constants.expoConfig?.version`, so an OTA can't change the displayed version without a native build (or a separate JS "update tag"). Verify the hash before publishing: `node -e "require('@expo/fingerprint').createFingerprintAsync(process.cwd(),{platforms:['android']}).then(f=>console.log(f.hash))"` and compare to the installed build's runtime.
- **`expo.extra.otaBuild` + `expo.extra.releaseNotes` ALSO shift the fingerprint** (found 2026-10-15). The project intends `extra.otaBuild` as a bump-every-OTA build label (read by `app-version.ts`/`update-release-info.ts`), but there is **no `fingerprint.config.js`/ignore**, so `extra` IS hashed — adding them (commit c5aa037) silently broke OTA delivery to installed `9796be6d…` devices. To ship the 2026-10-15 OTA I had to **strip `otaBuild`/`releaseNotes` from `app.json` extra** (fingerprint back to `9796be6d…`), so the in-app build label falls back to `version` (1.1.2) for that push. Proper fix (deferred): add a fingerprint ignore for those two `extra` keys + cut one new APK baseline, then OTA labels work again.
- **Removing a native dep from `package.json` shifts the fingerprint too** — dropping `expo-local-authentication` (when the App Lock UI was removed) changed the hash; **restored it in package.json** (unused native code) so the OTA still matched installed devices. Drop such deps only when cutting a new APK.

- **⚠️ LOCAL fingerprint no longer reproduces the APK's (found 2026-11-03).** `@expo/fingerprint` now computes `bb948bc6…` on THIS machine for the EXACT build-commit config (`f9579179d`, the Oct-5 indus APK) — but EAS cloud computed `9796be6d…` for that same tree (confirmed `app.json`+`package.json` byte-identical to the baseline I diffed). So the local-vs-EAS environments diverged (clean clone + different pnpm peer-path hashes in `node_modules/.pnpm/…`); the "compute the hash locally and compare to `9796be6d`" advice above is now UNRELIABLE and will mislead. **Source of truth for the installed runtime = `eas build:list --platform android --json`** (field APK = v1.1.2, runtime `9796be6d…`, profile `indus`, built 2026-10-05). Because of this gap, any `eas update` from this machine under `runtimeVersion.policy: fingerprint` tags the update with a hash that will NEVER equal `9796be6d…`, so it silently misses all field devices.
- **✅ ROBUST FIX — pin `runtimeVersion` to the literal string to OTA installed devices.** OTA delivery is plain string equality between the update's runtimeVersion and what the APK embedded. So temporarily set `app.json` `"runtimeVersion": "9796be6d1e9ae1268f9aab0b2200425496b09588"` (replacing the `{policy:"fingerprint"}` object), run the ship command, then revert. This sidesteps fingerprint computation entirely and reliably reaches the phones. **Safety rule: the published JS must not call any native module absent from that Oct-5 APK** — before pinning, diff `package.json` deps `f9579179d..HEAD` and confirm no NEW native module is referenced in `apps/mobile/src` (publish from a tree with such deps removed, e.g. strip PostHog's `posthog-react-native`/`expo-localization`). Note: an OTA ships the WHOLE current JS bundle, not one change.
- **Systemic fix (deferred, recommended):** move off `runtimeVersion.policy: fingerprint` to a fixed policy (explicit string per release, or `appVersion`) so local `eas update` and EAS `eas build` agree — otherwise every future OTA has this local/cloud mismatch.
