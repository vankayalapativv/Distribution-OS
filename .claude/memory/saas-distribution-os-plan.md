**Distribution OS** — the plan to turn this single-company system into a multi-enterprise **SaaS**. Full spec = **`docs/SAAS-PLAN.md`** (source of truth; this note is the pointer + the non-obvious bits). **Status: Phase 0 PLANNING ONLY — do NOT write code.**

**Build approach:** CLONE this whole codebase into a NEW repo/project, rebrand "Sri Aparajita" → "Distribution OS", owner supplies fresh API keys (Razorpay/Neon/Cloudflare/Neon Auth/EAS/Play/PostHog/maps). The **existing Sri Aparajita deployment stays untouched**. Terminology: a paying company = an **enterprise** (never "tenant"); isolation key = **`enterprise_id`**. ⚠️ This **reverses [[teams-territories-removed]]-era Hard Rule #6** (no org/multi-tenant scaffolding) — update AGENTS.md Hard Rule #6 in Phase 1 so an agent doesn't "clean up" `enterprise_id`.

**Locked decisions (owner):** one shared app for many enterprises; fully custom price per enterprise (per-seat OR flat, any amount/day); self-serve signup → owner-approved pending queue → billable immediately (no trial); email+phone OTP verified at signup; manual monthly Razorpay billing (like today); login = **email OR phone + password, both globally unique** (phone+password is NEW — today email only); one shared mobile app, neutral brand, Play Store, enterprise resolved from login, one OTA for all; per-enterprise read-only MCP scoped to own data; one domain, enterprise-from-signed-in-user (no subdomains); separate owner cockpit on **`admin.`** subdomain (approve enterprises, set prices, view payments, impersonate — all audit-logged), built to grow.

**Phases (re-sequenced 2026-11-11 — onboarding+approval+billing merged):** 0 Plan (here) → 1 Clone & rebrand + wire keys + deploy single-company baseline → 2 Enterprise foundation (`enterprises` table, `enterprise_id` on ~60 tables INCL. **`users`** + every query, auth carries it, scoped helper + Postgres RLS, email-or-phone login) → **3 Onboarding + approval + billing (ONE coupled phase** — signup wizard + email OTP → pending → owner dashboard approval queue (approve+set price / reject+reason) + enterprises list + GST-invoice upload + `enterprise_billing_config` + billing-v2 enterprise-aware; they ship together because approval sets price & starts billing) → 4 MCP per-enterprise scoping → 5 Mobile rebrand + Play Store + fix `runtimeVersion` policy (see [[expo-ota-updates]]) → 6 Hardening (cross-enterprise leak tests incl. MCP, backups) + deferred features (suspend/activate, impersonation, cross-enterprise analytics, phone OTP).

**✅ ISOLATION MODEL — LOCKED 2026-11-11: ONE shared DB + `enterprise_id` + Postgres RLS** (owner chose shared DB, reversing the 2026-11-10 DB-per-enterprise lean). Guardrails that MUST ship with it: a scoped SQL helper, RLS off a GUC (`app.enterprise_id`) set per request, and automated cross-enterprise leak tests. Accepted trade-off = logical isolation only (one missed filter leaks competitors' financial data → leak tests are non-negotiable) + whole-DB backups (can't PITR/restore/delete a single enterprise). The admin cockpit reads control-plane tables keyed by `enterprise_id` and runs as the platform owner OUTSIDE per-enterprise RLS. (DB-per-enterprise was considered for the privacy/per-enterprise-restore story but declined.)

**✅ CUSTOMER ONBOARDING — LOCKED 2026-11-11. Full spec = `docs/ONBOARDING-PLAN.md`; owner approval half = `docs/ADMIN-DASHBOARD-PLAN.md`.** Flow: **signup = login only** (name + email + phone + password, email & phone BOTH globally unique, **email OTP via Resend** for v1, phone OTP deferred) → creates a global user with NO enterprise/role yet → **multi-step onboarding wizard, EVERY field mandatory** ("collect all, mandatory!"), **auto-saved draft** (resume on next login, server-side keyed to user). Wizard collects: admin person; company legal name + **GSTIN (both mandatory here — optional in today's app)** + contact; registered address (incl. state/pincode); bank + UPI; invoice series (prefix+start) + **invoice T&C (pre-filled from `DEFAULT_TERMS`, editable)**; **≥1 godown**; **separate SE + Logistics field-tracking auto-stop times**; **custom dues-ageing bands** (variable count, each `from–to days` + label, replaces hard-coded 0-30/31-45/46-60/61+). **Submit** → `enterprises` row `status='pending'` + all config scoped by `enterprise_id`, signer-upper becomes first enterprise SUPER_ADMIN, nothing usable until approved. **Owner** (admin cockpit approval queue): **Approve + set price** (per-seat OR flat, one step → `active` + billing starts) OR **Reject + reason** (applicant edits + resubmits). Onboarding + cockpit built TOGETHER.

**✅ MCP IN THE SAAS — LOCKED 2026-11-11. Full spec = `docs/MCP-SAAS-PLAN.md` (grounded in real `apps/mcp` code).** Today: one worker `sri-aparajita-mcp`, **single shared passphrase** → hardcoded `userId:"sri-aparajita-owner"`, **`run_sql` runs ARBITRARY raw SQL** against the Neon read replica (`REPLICA_DATABASE_URL`) — read-only is physical but **NOTHING scopes rows** = the #1 SaaS isolation risk (raw SQL bypasses RLS). Go-live GATED on an MCP cross-enterprise leak test. Open: replica-can-set-GUC? (else scoped reader on primary); GRANT SELECT-only belt; per-enterprise rate cap. Reuses the Phase-2 RLS layer, does NOT invent its own scoping.

**✅ CONSISTENCY DECISIONS — LOCKED 2026-11-11 (cross-doc review found 4 real gaps):** (1) **ONE PERSON = ONE ENTERPRISE** — email/phone globally unique for login, but `users` carries `enterprise_id` + is **RLS-scoped** (NOT global as first drafted), so `select * from users` can't leak people across enterprises (critical for the MCP leak-test); a person in two enterprises needs two logins. Repricing note added to docs/ADMIN-DASHBOARD-PLAN.md. Also fixed stale wording: signup verify = **email OTP v1** (phone deferred), not "email+phone OTP".

**⚠️ OVERDUE-MODEL CHANGE (locked, ripples into existing code):** remove the company-wide **`credit_overdue_days` grace** — a customer is overdue + credit-blocked the moment an invoice passes **that customer's OWN `credit_days`** (`today > due_date`, grace=0; "block right at their terms"). Touches 3 places that add the global grace today: mobile credit gate `getCustomerCreditStatus` (`services/customers.ts`), dues ageing (age = days past due_date, bucketed into the enterprise's configured bands), mobile oldest-bucket dues (`/dues/me/*`). **SCOPE: Distribution OS (SaaS clone) ONLY — the live Sri Aparajita app keeps its 60-day grace, untouched (locked 2026-11-11).** Dues "bands are overdue money only"; the **9 AM dues sweep** (`runDuesMaintenance`, notifies SE on UPWARD band crossing) is a FIXED platform job, NOT an onboarding field — it just reads the bands.
