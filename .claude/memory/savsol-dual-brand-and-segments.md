Sri Aparajita sells **two oil brands: Fuchs + Savsol** (dual-brand catalogue). Done 2026-10-09; the user drove this and confirmed it belongs to **Sri Aparajita, NOT Sree Balaji** (Sree Balaji = Idemitsu oils + Hero parts — a different scope; do not port Fuchs/Savsol there).

**Brand switch (Fuchs ↔ Savsol):**
- **API**: `GET /products/paged` takes a `brand` query param (exact `p.brand =`, blank = all) in `apps/api/src/services/products.ts` `listManagedProductsPaged` + the `/paged` route. `GET /orders/products` (`listProducts` → `mapProductRow` in `orders-shared.ts`) now returns `brand` for the mobile order form.
- **Web**: Products catalogue (`products-catalogue-table.tsx` + `use-catalogue-table.ts`) has a **searchable brand combobox** (`brand-filter-select.tsx`, wraps the shared `OrderSearchCombobox` — matches the app's other pickers; the plain shadcn `<Select>` was replaced 2026-10-09). Options All brands / Fuchs / Mahindra First Choice / Savsol, oils-only, backed by `GET /brands?category=oils`; URL filter key `brand`, sentinel `ALL_BRANDS="__all__"`. Brand filter is in `FILTER_KEYS`.
- **Mobile**: New Order "Pick" screen is organised by **brand (company) TABS** (`catalogue-header.tsx` horizontal underline tabs = `availableBrands`, dynamic from the oils: Fuchs / Savsol / Mahindra First Choice / …). **The old `Oils | Bearings` tabs were removed** (2026-10-09, part 2) and **bearings dropped from the order screen entirely** (oils-only client) — `catalogue-list.tsx` is products-only, `use-order-queries.ts` no longer fetches bearings, `new.tsx` passes `bearings={[]}` to Review. Default tab = first brand alphabetically; switching brand resets the segment filter. Segment chips (All/Car/2W/…/Coolant/Grease) kept as a sub-filter within the selected brand. `availableSegments` + `filteredProducts` derive from the selected brand's products. `Product.brand` added to `apps/mobile/src/lib/order/types.ts`. (This replaced the earlier intermediate "brand segmented control inside the Oils tab" — brands are now the tabs themselves.) **Bearings removal here is UI-only on the order screen; the rest of the app's bearings code is untouched** (the app-wide removal in docs/BEARING-REMOVAL-PLAN.md is still deferred).

**Coolant + Grease are now catalogue segments** (product-type segments like Gear Oil, beyond the canonical six). Added to ALL NINE segment enumerations: api `products.ts` ALLOWED_SEGMENTS, api `targets.ts` + `dashboard-analytics.ts` OIL_SEGMENTS, web `chip-toggle.tsx` PRODUCT_SEGMENTS + `targets-api.ts` OIL_SEGMENTS + `orders-create-helpers.ts` SEGMENT_OPTIONS, mobile `performance.ts` OIL_SEGMENTS + `order/types.ts` SEGMENT_ORDER + `segment-sales.ts` SEGMENTS. So Targets now shows Coolant/Grease rows too (keeps their litres honest). `segment` is a plain `text` column — no DB enum/CHECK. See [[oil-segment-canonical-six]].

**GOTCHA — mobile brand tabs REQUIRE the API deploy.** The mobile order screen builds the Fuchs/Savsol tabs from each product's `brand` on `GET /orders/products`; that field was added in the same commits but the **Cloudflare Worker API had to be redeployed**. After the OTA but BEFORE the API deploy, the order screen (correctly running new code — Oils/Bearings tabs gone) showed NO brand tabs and all products mixed A–Z, because `availableBrands=[]` when `brand` is absent. **Verified fixed 2026-10-09 once the user deployed `apps/api`** — order screen on the production OTA build now shows Fuchs/Savsol tabs with per-brand segment chips. (Debug build had shown tabs earlier only because its `.env` `EXPO_PUBLIC_API_URL=http://10.0.2.2:8787` points at the LOCAL API; the production build uses the deployed Worker.) Lesson: an OTA that depends on a new API field isn't "done" until the API is deployed too.

**KEY GOTCHA learned 2026-10-09 — version bump vs OTA are mutually exclusive here.** `runtimeVersion.policy="fingerprint"` and **@expo/fingerprint@0.20.3 INCLUDES `app.json` `expo.version` in the hash**: bumping version 1.1.2→1.1.3 changed the android fingerprint to `bf4dc3c6…` ≠ installed `9796be6d…`, so an OTA at the bumped version would NOT reach current devices. To ship via OTA you MUST keep `version` at 1.1.2 (we reverted the bump). The Settings page shows `Constants.expoConfig?.version` (= app.json version), so it stays 1.1.2 after an OTA. To show a higher version number you need a NEW native build (APK) at 1.1.3; alternatively add an OTA-updatable "update tag" in Settings (JS-only, doesn't touch the fingerprint). See [[expo-ota-updates]].
